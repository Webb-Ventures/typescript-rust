# 0006: ts-r-lint

Status: Proposed (drafted for M4; awaiting review)
Owners: `ts_r_lint` (engine, rules, config), `ts_r_lint_cli` (binary)

## Context

M4 replaces `eslint` + `typescript-eslint` (and `oxlint` / `biome lint`) for the rules most
projects actually run: ESLint `recommended` and typescript-eslint `recommended` / `strict`.
Projects keep their existing config files. Constraints:

- **From scratch.** We may not read or port ESLint, typescript-eslint, oxlint or Biome source.
  Behaviour comes from the docs, the published rule tests (used as data only) and observed
  output of the real tools.
- **Drop-in output.** Rule ids, messages, positions, fixes, exit codes and the JSON format must
  match ESLint so CI scripts, editors and problem matchers keep working.
- **No binder or checker yet.** Scope-based rules (no-undef, no-unused-vars, prefer-const, ...)
  need scope analysis now. Type-aware rules must plug into the shared checker later without
  touching the rule API.

## Decision

### Rule API (`rule.rs`)

```rust
pub struct RuleDef { pub meta: RuleMeta, pub create: fn(&[Value]) -> Result<Box<dyn Rule>, String> }
pub struct RuleMeta { name, docs, fixable, has_suggestions, requires_types, presets, category }
// requires_types: set with `meta(..).typed()`; presets include the *TypeChecked configs.

pub trait Rule: Send + Sync + Debug {
    fn kinds(&self) -> &'static [NodeKind] { &[] }       // enter() is called for these
    fn exit_kinds(&self) -> &'static [NodeKind] { &[] }  // exit() is called for these
    fn enter(&self, node: NodeId, cx: &mut Ctx) {}
    fn exit(&self, node: NodeId, cx: &mut Ctx) {}
    fn run_file(&self, cx: &mut Ctx) {}                  // once per file, after the walk
    fn has_run_file(&self) -> bool { false }
}
```

- `meta.name` is the ESLint rule name and is the id everywhere: config, directives, output.
- `create` validates the options array (everything after the severity). It returns an error
  for invalid options; the rule is then skipped with a note, like ESLint's config validation
  error but without failing the run.
- Instances are cached per (rule, options JSON) and shared across files and threads. Rules
  hold no mutable state.
- `Ctx` exposes the AST, source, parent map, line index, environment (`LintEnv`: source
  type, ECMAScript version, globals, TypeScript parser, settings), the lazily built semantic
  model, and `TypeInfo`. `cx.report(span, msg).id("messageId").fix(..).suggest(..)`.
- Positions are byte spans; output converts them to ESLint's 1-based line and UTF-16 column.
- A typescript-eslint extension rule (`@typescript-eslint/no-unused-vars`, `no-redeclare`,
  `no-array-constructor`, `no-unused-expressions`, `no-useless-constructor`,
  `no-dupe-class-members`) shares the core rule's implementation: the core module exposes a
  `pub(crate)` rule type or a `create_ts` constructor with a TypeScript switch, and the
  `ts_*` module only declares the `RuleDef`. Behaviour that differs is keyed on that switch,
  never on the file name.
- Core rules keep ESLint's behaviour on TypeScript code when users enable them there: core
  `no-unused-vars` reports signature parameters and parameter properties, core
  `no-redeclare` counts type aliases, interfaces, enums and namespaces.

### Engine (`engine.rs`)

- Per file: parse, build `ParentMap`, parse inline config (directives, `/* eslint */`,
  `/* global */`, `/* exported */`), then **one** `ts_r_ast::walk` that dispatches each node
  to the rules registered for its `NodeKind` (tables built once per rule set). Then run
  `run_file` rules.
- A parse error produces a single fatal `Parsing error: ...` diagnostic, as in ESLint.
- With the TypeScript parser configured, `.js`/`.jsx` files parse the way typescript-eslint
  parses them: tsc's grammar for JavaScript files (JSX on, TypeScript syntax accepted, no type
  arguments on expressions, so `new Array<Foo>(1)` is two comparisons), without tsc's TS8xxx
  "can only be used in TypeScript files" errors, which typescript-eslint does not treat as
  parse errors (`ts_r_parser::TsInJs::Allow`, request R8). Without it they stay JavaScript.
- Directives are applied after all rules run. Unused `eslint-disable` directives are reported
  (default `warn`, `linterOptions.reportUnusedDisableDirectives`) with ESLint's messages and
  removal fixes. Unused directives naming rules ts-r-lint does not run are not reported, since
  we cannot know whether ESLint would have reported a problem.
- Fixes: a pass sorts fixes by range and skips any fix that starts at or before the end of the
  previous applied fix. `--fix` re-lints and re-applies until no fix applies, at most 10
  passes (ESLint's limit).
- Files are linted in parallel on `min(4, cores)` scoped threads (`--threads`), each with a
  256 MB stack; results are reported in path order.

### Scope analysis (`semantic/`)

`trait Semantic` exposes scopes, symbols (with declaration kinds and flags), references (read,
write, type, export, JSX, ...), and resolution (symbol, configured global, unresolved).
`semantic/local.rs` is a **temporary** single-pass implementation built lazily per file the
first time a rule asks for it. When `ts_r_binder` lands, an adapter implements `Semantic` over
the binder's tables and `local.rs` is deleted; rules do not change.

### TypeScript lib globals (`lib_globals.rs`)

On files parsed by the TypeScript parser, typescript-eslint's scope analysis defines the
TypeScript lib's global names; core `no-undef` and `builtinGlobals` see them. Observed with
ESLint 10.12 and typescript-eslint 8.71:

- **Which libs.** `parserOptions.lib` if set. Otherwise, with `parserOptions.project` or
  `projectService`, the file's tsconfig: its `lib`, else `target`'s default lib
  (`es2020.full` and so on, which include the DOM). Otherwise `esnext` (no DOM).
  `/// <reference lib>` directives are followed. `ecmaVersion` does not matter.
- **What they define.** A lib name with a type meaning (interface, type alias, class, enum,
  namespace) is a global variable. It satisfies type references, and value references only
  when it also has a value meaning (`Map`, `Intl`); `PropertyKey` used as a value is
  undefined. A name with only a value meaning (`document`, `structuredClone`) is not defined
  at all. Configured globals (`globals`, ESLint's `ecmaVersion` built-ins) satisfy both kinds.
- **`builtinGlobals`** (`no-redeclare`, `@typescript-eslint/no-redeclare`) counts every lib
  global variable, whatever the redeclaration's kind (`type NodeListOf = 1`, `var Map`).
- Core `no-undef` reports unresolved type references as well as value references.

The names come from a table generated by `cargo xtask codegen lint-globals` from the pinned
tsc 7 lib files (per lib file: references, type names, value names), checked in as
`lib_globals_generated.rs` and verified by `cargo xtask codegen --check`. Lib sets are
resolved once per distinct set; tsconfigs once per path (with `project`/`projectService`
the engine resolves the lib per file from the nearest or listed tsconfig).

### Type information (`types.rs`, `typed/`)

Type-aware rules ask an object-safe `TypeInfo` trait (every method has a "don't know"
default; `NoTypeInfo` answers nothing):

```rust
pub trait TypeInfo {
    fn is_available(&self) -> bool;
    fn type_at(&self, node: NodeId) -> Option<Ty>;            // expression, binding, type node
    fn contextual_type(&self, node: NodeId) -> Option<Ty>;
    fn resolved_signature(&self, call: NodeId) -> Option<Sig>;
    fn symbol_at(&self, node: NodeId) -> Option<Sym>;
    fn flags(&self, t: Ty) -> TypeFlags;  fn union_members(&self, t: Ty) -> Vec<Ty>;
    fn property_of_type(&self, t: Ty, name: &str) -> Option<Sym>;
    fn signatures(&self, t: Ty, construct: bool) -> Vec<Sig>;
    fn is_assignable(&self, from: Ty, to: Ty) -> bool;  fn type_to_string(&self, t: Ty) -> String;
    fn symbol_decls(&self, s: Sym) -> Vec<Decl>;  fn option(&self, name: &str) -> Option<bool>;
    // ... awaited_type, apparent_type, base_constraint, index_type, type_args, ...
}
```

`Ty`, `Sym` and `Sig` are the checker's own ids (`ts_r_types`); `typed::CkTypes` implements
the trait over one checker worker (`ts_r_checker::checker::Ck`) that has just checked the file,
so rules see exactly the types the check computed, without copying. Rules share helpers in
`type_util.rs`. **A type the checker could not compute (`TypeId::UNRESOLVED`) never causes a
report**: helpers treat it as "don't know".

**Projects.** `project::lint_paths` hands every file whose config enables a type-aware rule
to `typed::driver::lint_projects`, which groups files by the tsconfig typescript-eslint would
use (`parserOptions.project` entries or, with `projectService`, the nearest
`tsconfig.json`) and handles one project at a time:

1. `typed::load_project` loads the tsconfig's program and arranges it on the process-wide
   shared levels of `ts_r_history` (lib and `node_modules` files are parsed, bound and typed
   once per run and reused by every project with the same files and options).
2. `typed::check_and_lint` checks every file of the project on up to 4 threads (one checker
   worker each) and lints the requested files right after their check, through the program's
   own AST (so node ids match). A checker panic is caught per file: the file is linted without
   types and the project counts as a mismatch.
3. **Parity.** Our project diagnostics are compared with the user's
   `tsc -p <tsconfig> --noEmit` (their `node_modules/typescript`, run on up to `--threads`
   (max 4) background threads, one tsc process each, while we check, capped at 600 s and 4 GB) as a multiset of `file(line,col): TScode`. Match:
   the typed results are reported. Mismatch: the project's files are linted without type-aware
   rules and each such rule is reported once as unsupported in that project, so a checker gap
   never produces wrong reports. No TypeScript installed or tsc failing: our checker is used
   (as in the editor). Verdicts are cached in `ts_r_cache` (`lint/parity/`), keyed by the
   tsconfig and its `extends` chain, the lockfile, the TypeScript and ts-r versions, and
   reused while our own diagnostics for the project are unchanged (otherwise tsc runs again).
   `TS_R_LINT_PARITY=off` skips the check; `=require` treats "unknown" as a mismatch.
4. Files not in the project's program, files starting with a BOM, and type-aware rules on
   files without `project`/`projectService` are linted without types (the rules are listed as
   unsupported, with the reason).

With `--fix`, a project is checked, every file's fixes applied in memory, and the project
re-checked on the fixed text (an overlay file system), up to 10 passes; the caller writes the
files. `--no-type-check` turns type-aware rules off. `TS_R_LINT_TIMING=1` prints per-project
load/check/parity times. Each tool is self-contained (design record P8): `ts-r-lint` links
the checker crates itself and needs no daemon; the editor runs the same rules on the
language server's checker.

### Config (`config/`)

- **ESLint flat config** (`eslint.config.{js,mjs,cjs,ts,mts,cts}`): ESLint 10 semantics, the
  nearest config at or above each file. All configs found are evaluated in **one** Node process
  (`eslint_eval.rs` embeds a small ESM script) that imports each config and prints the
  flattened array as JSON (functions become notes; parsers become their `meta.name`). Results
  are cached in `ts_r_cache` namespace `lint-config`, keyed by script version, config path,
  config content and the nearest lockfile; the cache entry stores hashes of every local file the
  config imported, and is invalid when any changed. A Node without `module.registerHooks`
  cannot report those imports, so its results are not cached. Node comes from `TS_R_NODE` or
  `PATH`; a wrapper (for example `scripts/limit.sh --`) from `TS_R_LINT_NODE_WRAPPER`.
- Config objects are merged per file as ESLint does: `files` / `ignores` globs
  (minimatch subset in `glob.rs`, relative to the config's directory), global ignores, a file
  is linted only if a non-universal `files` pattern matches, later objects override earlier
  ones, rule options replace earlier options. Built-in defaults: `**/node_modules/`, `.git/`;
  `.js`/`.mjs` are modules, `.cjs` CommonJS.
- **Rule names** map through `mapping.rs`: ESLint core and `@typescript-eslint/` names map to
  ours by name. Anything else is reported once per config on stderr with a reason: needs type
  information, plugin not implemented, not implemented yet, unknown.
- **oxlint** (`.oxlintrc.json`): `rules` (`eslint/`, `typescript/` prefixes or bare names),
  `categories` (correctness defaults to warn), `ignorePatterns`, `overrides`, `globals`.
- **Biome** (`biome.json(c)`): `linter.enabled`, `linter.rules` groups and `recommended`
  through a table of Biome rules with an ESLint equivalent, `files.includes` negations and
  `overrides`.
- Lookup order per file: nearest ESLint config; else nearest oxlint config; else nearest Biome
  config; else the built-in default (ESLint recommended + typescript-eslint recommended for
  TS files). `--config` uses one config for every file, with patterns relative to the cwd.
- `.gitignore` files are honoured while walking directories (`--no-gitignore` turns this
  off). Explicitly named ignored files get ESLint's "File ignored ..." warning.
- `languageOptions.parserOptions` that change scope analysis are read: `ecmaFeatures.
  globalReturn`, and for the TypeScript parser `jsxPragma` (default `React`),
  `jsxFragmentName`, and `emitDecoratorMetadata` + `experimentalDecorators` (exposed as
  `LintEnv::decorator_metadata`).

### Output (`output.rs`) and CLI

- Formats: `stylish` (default, ESLint layout without colours), `json` (ESLint's result
  objects), `sarif` (2.1.0), `github` (workflow commands).
- Exit codes: 0 clean; 1 errors, or more warnings than `--max-warnings`; 2 usage or fatal
  config error. `--quiet` does not run warn-level rules and hides warnings.

## Invariants agents must keep

- Rule ids, messages, message ids, positions, fixes and suggestions match ESLint; the rule
  oracle (`tests/rule_oracle.rs`) per-rule pass counts never drop below the baseline.
- Rules are stateless and registered in `rules::ALL`; no rule walks the whole tree on its own
  when `kinds()` would do.
- Rules use the semantic model only through the `Semantic` trait and type information only
  through `TypeInfo`.
- Fixes in one pass never overlap; at most 10 fix passes.
- The source of ESLint, typescript-eslint, oxlint or Biome may be read to understand a rule,
  never ported.

## Alternatives

- **Port rule implementations from oxlint or Biome.** Fastest route, but excluded by the
  from-scratch rule (reading them to understand a rule is allowed; porting is not).
- **Evaluate flat configs with an embedded JS engine.** Configs import plugins, `globals`,
  `typescript-eslint` and the project's own files; only the project's Node resolves those
  faithfully. One Node run per config change (cached) costs ~100-300 ms once.
- **Per-rule traversals.** Simpler rules, but 90 walks per file; one walk with kind dispatch
  keeps the cost per node to a table lookup.
- **Wait for the binder.** Would block no-undef / no-unused-vars / prefer-const, the most
  used rules. The temporary scope model is isolated behind a trait instead.
